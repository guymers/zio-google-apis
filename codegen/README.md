# Codegen

A protoc plugin that generates Scala 3 case-class messages and enums, plus [ZIO](https://github.com/zio/zio) gRPC clients, from Google protobuf definitions.

## Build integration

`build.sbt` builds `codegen/assembly` and writes a `protoc-plugin.sh` wrapper that runs the jar. Every protobuf project passes it to protoc with `--plugin=protoc-gen-zga=...`, and generated sources are formatted with scalafmt afterward.

Plugin options go in `--zga_opt` as `;`-separated `key=value` pairs, each given at most once:

- `class_prefix` and `pkg_name` generate service clients in addition to messages and enums, see [Service clients](#service-clients). Every other option requires both.
- `services_only` is a `,`-separated list of `.proto` files to generate only service clients for, their messages come from a dependency.
- `routing` is a `,`-separated list of `method:field` or `method:field:path_template` routing parameters for routing that the proto does not declare. `method` is the method's full name.

sbt-protobuf's cache only tracks the `.proto` files and protoc options, so the build drops it whenever the plugin jar changes. `sbt <client>/compile` therefore regenerates and compiles without a `clean`.

Generated sources are written to `target/out/jvm/scala-<version>/<project>/src_managed/main`.

## Generated code

The package comes from `java_package`, falling back to the proto `package`. `google.*` and `com.google.*` packages are moved under `zga.google` so they cannot clash with Google's own Java classes on the classpath, and the API version segment (`v1`, `v2`, `v1beta1`, `v1p1beta1`, ads' `v17`, ...) is dropped, so `google.cloud.secretmanager.v1` generates into `zga.google.cloud.secretmanager`. Ads' extra `googleads` segment is dropped too, so `google.ads.googleads.v26` generates into `zga.google.ads`. Generated names therefore do not change when an API moves to a new version.

### Messages and enums

For each `.proto` file, `Generator.scala` emits the message case classes and enums. Each message has a `given` `zga.common.MessageCodec` with explicit code reading, writing and sizing its fields, generated by `CodecGenerator.scala`, so no descriptor is embedded, see [Message codecs](#message-codecs). A message without fields shares the codec `MessageCodec.empty`, rather than a class of its own.

A message carries only the fields the `.proto` declares, so a field that a newer server sends and this project does not know about is dropped when the message is encoded again.

A field of type `google.protobuf.Timestamp` is a `java.time.Instant`, and one of type `google.protobuf.Duration` is a `java.time.Duration`. They are not generated: their `MessageCodec`s are written by hand in `common` and convert to and from the protobuf `seconds` and `nanos`; a negative `java.time.Duration` is written in the sign-normalized form that the proto requires. Like protobuf-java, they read any `seconds` and `nanos`, even outside the ranges the proto allows, but `java.time` normalizes them, so a `Timestamp` of 1 second and -1 nanos is read as 0.999999999 seconds and written back as 0 seconds and 999999999 nanos. Only a value `java.time` cannot represent, such as a `Timestamp` beyond `Instant`'s range, fails to read as an `InvalidProtocolBufferException`, like any other invalid message. `Date`, `TimeOfDay`, `DateTime` and `TimeZone` stay generated case classes, as `java.time` cannot hold every value they allow: a `Date` with a year, month or day of 0, which protobuf's default values make unavoidable, a `TimeOfDay` of 24:00 or a leap second, or a `DateTime` in local time, without a year, or in a named time zone.

`DayOfWeek` is a `java.time.DayOfWeek` and `Month` a `java.time.Month`, wrapped in an `Option` because the proto's unspecified value has no counterpart. A number with no `java.time` value fails to read as an `InvalidProtocolBufferException`. Reading it as `None` would write it back as the unspecified value, and no weekday or month will ever be added. Proto values are matched to `java.time` values by name. Only an open enum can be mapped; codegen fails for a closed one. A mapped enum field with explicit presence (proto3 `optional`) is an `Option` of that `Option`, like any other field with presence, so an unset field is `None` and one set to the unspecified value is `Some(None)`.

An open enum (proto3, or editions without `enum_type = CLOSED`) keeps numbers it does not know, so a message read from a newer server and written back does not lose the value:

```scala
sealed trait Kind { def value: Int }
object Kind {
  enum Recognized extends Kind { case A, B; def value: Int = numbers(ordinal) }
  export Recognized.*                           // Kind.A == Kind.Recognized.A
  case class Unrecognized private[Kind] (value: Int) extends Kind
  private val numbers = Array(0, 5)             // omitted when the numbers are the ordinals
  def fromValue(v: Int): Kind                   // Unrecognized(v) when unknown
}
```

The values are plain cases, which share one class, as a case with constructor arguments (`case A extends Recognized(0)`) compiles to a class of its own and so to thousands of classes in the large APIs.

A closed (proto2) enum is a plain Scala `enum`, as protobuf stores an unknown closed enum number in the message's unknown fields instead, so the number is dropped like any other unknown field.

### Message codecs

A codec reads, writes and sizes each field with protobuf-java's `CodedInputStream` and `CodedOutputStream`, from the field's number, proto type, cardinality and packing in the descriptor at build time. The runtime in `common` is:

- `MessageCodec`, which every codec extends
- `ProtoReader`, which limits how deeply messages nest, as protobuf-java does
- `Sizes`, which records the size of each nested message once while sizing, so that writing does not recompute it
- `Oneof`, which every oneof trait extends
- the hand-written codecs of `Timestamp` and `Duration`, see [Messages and enums](#messages-and-enums)

`toByteArray` computes the message's size first and writes into an array of exactly that size, so a nested message's length is known before it is written. Fields are written in field number order, a oneof at its first member's number, so bytes match protobuf-java except when a oneof's members are numbered around another field. Map entries are written in the map's iteration order, as protobuf-java does by default.

HotSpot never JIT compiles a method of more than 8000 bytes of bytecode. The generator estimates how much bytecode each field adds, and when a codec's methods would come close to that limit, it splits the fields into parts and gives each part its own method:

- `serializedSize` and `writeTo` call the part methods one after another, so fields are still written in field number order.
- `readFrom` cannot share local variables between methods, so it reads into a nested class instead. The class holds a variable per field, and each of its methods reads the tags of one part.

A codec whose `serializedSize` and `writeTo` are split is moved to a file of its own, to keep the message's file smaller. Its object is named after the message and the messages it is nested in, so the codec of `Outer.Inner` is `OuterInnerMessageCodec`.

### Oneofs

A proto `oneof` becomes a nested sealed trait with a case class per member field, and a single `Option` case class parameter:

```scala
case class Operation(result: Option[Operation.Result] = None)
object Operation {
  sealed trait Result extends zga.common.Oneof
  object Result {
    case class Error(value: Status) extends Result { /* sizes and writes field 4 */ }
    case class Response(value: protobuf.Any) extends Result { /* sizes and writes field 5 */ }
  }
}
```

`None` is a oneof with no member set, which is distinct from a member set to its default value. Each case sizes and writes its own member, so the message's codec calls one method for the oneof however many members it has. The codec reads a member as replacing any other, merging a message member read again into its previous value. A oneof cannot be a union of the member types, as members often share a type, such as several `string` members.

A oneof parameter defaults to `None` unless the oneof is required. Then it has no default, the same as a required field.

Protobuf has no way to mark the oneof itself as required: a oneof cannot be `required`, and `google.api.field_behavior` can only be set on fields. Google APIs instead mark every member of the oneof `(google.api.field_behavior) = REQUIRED`. The generator therefore treats a oneof as required when all of its members are marked, not counting deprecated members. A oneof with only some members marked is not required.

A proto3 `optional` field, which the descriptor models as a synthetic oneof, remains an `Option` field.

### Field defaults

Generated case classes give every field a default value, except fields marked `(google.api.field_behavior) = REQUIRED`. A proto2 `required` field fails codegen, as does a group field.

Required collections keep their empty default, as a required repeated field does not have to be non-empty.

### Large messages

A parameter takes one slot, or two for a `Long` or a `Double`. The JVM allows a method 254 slots, but HotSpot's C2 compiler gives up on a method with many arguments well before that, and then neither compiles the case class constructor nor inlines it into its callers. So a message whose fields take more than 64 slots is split into consecutive chunks of at most 64 slots, one nested case class per chunk named `Part1`, `Part2`, and so on, and the message exports them:

```scala
case class Metrics(
  part1: Metrics.Part1 = Metrics.Part1(),
  part2: Metrics.Part2 = Metrics.Part2(),
) {
  export part1.*
  export part2.*
}
```

A chunk's parameters keep the whole proto field name. The message's codec reads and writes the chunks' fields as its own, in field number order whichever chunk they are in, and builds the chunks once all fields are read.

Exporting chunks makes a field read as the message's own, `metrics.activeViewCtr`. Only reads, though: `copy`, `apply` and pattern matching still take the chunk parameters. Each real `oneof` counts as one parameter and can be placed in a chunk alongside ordinary fields. If the chunk parameters themselves exceed the limit, they are grouped again. A message at the limit is left as one case class.

Separately, a codec's methods are split when a message has too many fields for HotSpot to JIT compile them, see [Message codecs](#message-codecs).

### Service clients

When client options are set, `ZioGrpcGenerator.scala` emits a file per `.proto` with services, in `zga.client.<pkg_name>`. Each service gets:

- `trait <X>Client` and its implementation `<X>ClientLive`, whose `withAuth` returns a client that authenticates differently
- `object <X>Client` with `create`, `layer`, `unauthenticated`, which returns a client that is given its authentication later with `withAuth`, and `object Grpc`, which holds the `METHOD_*` descriptors, `ROUTING_*` parameters and `SERVICE` descriptor

Clients take a `<class_prefix>Channel` and use `zga.client.<pkg_name>.auth.<class_prefix>Authentication`. Both are handwritten in the client project.

Codegen fails with an error that names the collision when two generated names would be the same:

- two services that map to the same client name, even when they are in different protos
- two methods of a service that map to the same `Grpc` member
- a method that maps to `withAuth`, which every client already has
- two protos that map to the same Scala file

These are checked before any file is written.

### Request routing

Clients send routing parameters in the `x-goog-request-params` header, as described in [AIP-4222](https://google.aip.dev/client-libraries/4222). A method's parameters come from the first of these that applies:

1. A client-streaming method has no single request. Only the `routing` plugin option routes it with the values coming from the first request in the stream.
2. The method's `google.api.routing` option. Any parameters from the `routing` plugin option are added after its own. An option that declares no parameters turns routing off for the method.
3. The `routing` plugin option alone. It must route on every `google.api.http` path variable or codegen fails.
4. The variables of the method's `google.api.http` path, as the Google client libraries do. Each sends the whole field value keyed by its field path, for example `name=projects/p`. The primary path's variables come first and those of each `additional_bindings` rule follow. A variable is only sent once.

The `routing` plugin option is for routing that the proto does not declare, which the Google client libraries add by hand.

A method's parameters become its `ROUTING_*` value in the client's `Grpc` object. Each `zga.client.Routing.Parameter` reads a request field and can hold a path template that was parsed during codegen. An unknown field or a malformed template therefore fails codegen. At runtime `zga.client.Routing` matches the field values against their templates and encodes the header.

A parameter from `google.api.routing` or the plugin option must be a string field. An http path variable can also be an integer, bool or enum field.
