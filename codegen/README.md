# Codegen

A protoc plugin that generates Scala 3 case-class messages and enums, plus [ZIO](https://github.com/zio/zio) gRPC clients, from Google protobuf definitions.

## Build integration

`build.sbt` builds `codegen/assembly` and writes a `protoc-plugin.sh` wrapper that runs the jar. Every protobuf project passes it to protoc with `--plugin=protoc-gen-zga=...`, and generated sources are formatted with scalafmt afterward.

Plugin options go in `--zga_opt` as `;`-separated `key=value` pairs. `class_prefix` and `pkg_name` cause service clients to be generated in addition to messages and enums.

sbt-protobuf's cache only tracks the `.proto` files and protoc options, so the build drops it whenever the plugin jar changes. `sbt <client>/compile` therefore regenerates and compiles without a `clean`.

Generated sources are written to `target/out/jvm/scala-<version>/<project>/src_managed/main`.

## Generated code

The package comes from `java_package`, falling back to the proto `package`. `google.*` and `com.google.*` packages are moved under `zga.google` so they cannot clash with Google's own Java classes on the classpath, and the API version segment (`v1`, `v2`, `v1beta1`, `v1p1beta1`, ads' `v17`, ...) is dropped, so `google.cloud.secretmanager.v1` generates into `zga.google.cloud.secretmanager`. Ads' extra `googleads` segment is dropped too, so `google.ads.googleads.v26` generates into `zga.google.ads`. Generated names therefore do not change when an API moves to a new version.

### Messages and enums
 For each `.proto` file, `Generator.scala` emits the message case classes and enums. Each message has a `given` `zga.common.MessageCodec` with explicit code reading, writing and sizing its fields, generated by `CodecGenerator.scala`, so no descriptor is embedded, see [Message codecs](#message-codecs). A message without fields shares the codec `MessageCodec.empty`, rather than a class of its own.

A message carries only the fields the `.proto` declares, so a field that a newer server sends and this project does not know about is dropped when the message is encoded again.

A field of type `google.protobuf.Timestamp` is a `java.time.Instant`, and one of type `google.protobuf.Duration` is a `java.time.Duration`. They are not generated: their `MessageCodec`s are written by hand in `common` and convert to and from the protobuf `seconds` and `nanos`; a negative `java.time.Duration` is written in the sign-normalized form that the proto requires. `Date`, `TimeOfDay`, `DateTime` and `TimeZone` stay generated case classes, as `java.time` cannot hold every value they allow: a `Date` with a year, month or day of 0, which protobuf's default values make unavoidable, a `TimeOfDay` of 24:00 or a leap second, or a `DateTime` in local time, without a year, or in a named time zone. 

`DayOfWeek` is a `java.time.DayOfWeek` and `Month` a `java.time.Month`, wrapped in an `Option` because the proto's unspecified value has no counterpart. A number with no `java.time` value fails to read as an `InvalidProtocolBufferException`, as a weekday or month will never be added and a `None` would be written back as the unspecified value. Proto values are matched to `java.time` values by name. Only an open enum can be mapped; codegen fails for a closed one. A mapped enum field with explicit presence (proto3 `optional`) is an `Option` of that `Option`, like any other field with presence, so an unset field is `None` and one set to the unspecified value is `Some(None)`. A value `java.time` cannot represent, such as a `Timestamp` beyond `Instant`'s range, fails to read as an `InvalidProtocolBufferException`, like any other invalid message.

An open enum (proto3, or editions without `enum_type = CLOSED`) keeps numbers it does not know, so a message read from a newer server and written back does not lose the value:

```scala
sealed trait Kind { def value: Int }
object Kind {
  enum Recognized extends Kind { case A, B; def value: Int = numbers(ordinal) }
  export Recognized.*                           // Kind.A == Kind.Recognized.A
  case class Unrecognized private[Kind] (value: Int) extends Kind
  private val numbers = Array(0, 5)             // omitted when the numbers are the ordinals
  def fromValue(v: Int): Kind                   // Unrecognized(v) when unknown
}
```

The values are plain cases, which share one class, as a case with constructor arguments (`case A extends Recognized(0)`) compiles to a class of its own and so to thousands of classes in the large APIs.

A closed (proto2) enum is a plain Scala `enum`, as protobuf stores an unknown closed enum number in the message's unknown fields instead, so the number is dropped like any other unknown field.

### Message codecs

A codec reads, writes and sizes each field with protobuf-java's `CodedInputStream` and `CodedOutputStream`, from the field's number, proto type, cardinality and packing in the descriptor at build time. The runtime in `common` is only `MessageCodec`, `ProtoReader`, which limits how deeply messages nest, as protobuf-java does, `Sizes`, which records the size of each nested message once while sizing so that writing does not recompute it, and `Oneof`, which every oneof trait extends.

`toByteArray` computes the message's size first and writes into an array of exactly that size, so a nested message's length is known before it is written. Fields are written in field number order, a oneof at its first member's number, so bytes match protobuf-java except when a oneof's members are numbered around another field. Map entries are written in the map's iteration order, as protobuf-java does by default.

HotSpot never JIT compiles a method of more than 8000 bytes of bytecode, so the generator estimates the bytecode of each field's code and splits a codec's methods to stay well under that. When a message has too many fields for one method, `serializedSize` and `writeTo` call a method per part of the fields, in field number order, and `readFrom` reads into a nested class holding a variable per field, whose methods each read the tags of a part of the fields.

### Oneofs

A proto `oneof` becomes a nested sealed trait with a case class per member field, and a single `Option` case class parameter:

```scala
case class Operation(result: Option[Operation.Result] = None)
object Operation {
  sealed trait Result extends zga.common.Oneof
  object Result {
    case class Error(value: Status) extends Result { /* sizes and writes field 4 */ }
    case class Response(value: Any) extends Result { /* sizes and writes field 5 */ }
  }
}
```

`None` is a oneof with no member set, which is distinct from a member set to its default value. Each case sizes and writes its own member, so the message's codec calls one method for the oneof however many members it has. The codec reads a member as replacing any other, merging a message member read again into its previous value. A oneof cannot be a union of the member types, as members often share a type, such as several `string` members.

A oneof is never `required` in protobuf and has no options of its own, so a required oneof cannot be declared directly. As with a required field, a required oneof drops its `None` default. The generator treats a oneof as required when every member that is not deprecated carries `(google.api.field_behavior) = REQUIRED`; a deprecated member is ignored, and a lone required member among many does not make the oneof required.

A proto3 `optional` field, which the descriptor models as a synthetic oneof, remains an `Option` field.

### Field defaults

Generated case classes give every field a default value, except fields marked as required by the proto2 `required` label or by `(google.api.field_behavior) = REQUIRED`.

Required collections keep their empty default, as a required repeated field does not have to be non-empty.

### Large messages

The JVM limits a method to 254 parameter slots, counting a `Long` or a `Double` as two, so a message with more fields than that cannot be one case class. Such a message's fields are split into consecutive chunks of at most that many slots, one nested case class per chunk named `Part1`, `Part2`, and so on, and the message exports them:

```scala
case class Metrics(
  part1: Metrics.Part1 = Metrics.Part1(),
  part2: Metrics.Part2 = Metrics.Part2(),
) {
  export part1.*
  export part2.*
}
```

A chunk's parameters keep the whole proto field name. The message's codec reads and writes the chunks' fields as its own, in field number order whichever chunk they are in, and builds the chunks once all fields are read, so proto2 required fields can live in different chunks.

Exporting chunks makes a field read as the message's own, `metrics.activeViewCtr`. Only reads, though: `copy`, `apply` and pattern matching still take the chunk parameters. Each real `oneof` counts as one parameter and can be placed in a chunk alongside ordinary fields. If the chunk parameters themselves exceed the limit, they are grouped again. A message at the limit is left as one case class.

Separately, a codec's methods are split when a message has too many fields for HotSpot to JIT compile them, see [Message codecs](#message-codecs).

### Service clients

When client options are set, `ZioGrpcGenerator.scala` emits a file per `.proto` with services, in `zga.client.<pkg_name>`. Each service gets:

- `trait <X>Client` and its implementation `<X>ClientLive`
- `object <X>Client` with `create`, `layer` and `object Grpc`, which holds the `METHOD_*` descriptors, `ROUTING_*` parameters and `SERVICE` descriptor

Clients take a `<class_prefix>Channel` and use `zga.client.<pkg_name>.auth.<class_prefix>Authentication`. Both are handwritten in the client project.

Names are checked before anything is written: two services that would produce the same client name, two methods that would produce the same `Grpc` member, and two protos that would produce the same Scala file all fail codegen with the names that collided.

### Request routing

Google API routing (`google.api.routing`) becomes `ROUTING_*` values of `zga.client.Routing.Parameter`. Each is an accessor that captures a path template parsed during generation, so malformed templates or field paths fail codegen. At runtime `zga.client.Routing` only matches and encodes them into the `x-goog-request-params` header. Client-streaming methods are skipped, as they have no single request.

A method without a `google.api.routing` option falls back to the variables of its `google.api.http` path, as the Google client libraries do: each sends the whole field value keyed by its field path, e.g. `name=projects/...`. The variables of the primary path come first, then those of each `additional_bindings` rule, in order and without duplicates. Explicit routing parameters replace the http variables entirely, and a routing option that declares no parameters declares no routing at all, which is how a method opts out of the implicit http routing.
